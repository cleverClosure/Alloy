# Milestone 3: launch previews and bounded fixture supervision

Run `python3 runtime/session-service/run-session-proof.py`. The actual XPC service
installs digest-verified loopback fixture bytes through InstallationEngine,
resolves through LaunchCompiler and acquires leases through ContentStore. No
existing dependency is modified. Unsigned fixture inputs explicitly declare an
experimental profile, development release ring and draft evidence.

Named rows check the normal-mode refusal, preserved unsupported-policy report,
canonical export verification, real-game refusal, modified export and expiry,
normal three-process exit, idempotency/rejected conflict, startup failure,
per-process exact generation leases, TERM/KILL escalation, agent death, service
death/restart reconciliation, unattended watchdog expiry and lease-protected GC.
After uninstall, a live tree must retain its precise object; after stop, GC must
remove that digest and report zero leases. Every terminal fault check requires
all descendants to be dead, using their recorded kernel process identities.

The wrong-readiness control (`--negative-control`) deliberately expects a
runtime-ready export. It must fail only `coverage-gap-preserved`; the clean proof
must instead preserve false readiness and the nonempty unsupported-field list.
The unit suite additionally checks private record replacement, symlink/mode
refusal, and rejection of an identity with the current PID but a different start
time. All six Swift tests pass. The live proof reports
`pass=20 fail=0 total=20`; its wrong-readiness control reports
`pass=19 fail=1 total=20`, failing only `coverage-gap-preserved`.

Limits: fixed native cooperative fixture only; no arbitrary executable, Wine
policy enforcement, production verification or real-game launch. Preview inputs
are synthetic caller-supplied development evidence. The hard watchdog is 20
seconds, and every proof wait and outer suite has an explicit deadline. A private
launchd job is booted out and verified absent at fixture teardown.

After supervisor wiring, the registered boundary and operation regression suites
also pass: 9/9 and 38/38 named rows respectively. The registry completeness
self-test passes with 46 suites, and repository lint passes. No hosted workflow
or timeout budget was changed.

## Hosted host constraint

The first hosted run (37226370615) rejected preview compilation. Its existing
compiler host test independently reports `26.6.2 (25G83)`, arm64 and **7 GiB**.
The unchanged compiler requires at least 8 GiB for a local host-class identity;
this is also consistent with GitHub's standard arm64 runner specification.
The rejection is correct, and neither the host record nor the compiler minimum
is changed to make the full proof pass on unsupported hardware.

The registered session proof now names arm64 macOS with >=8 GiB as its prerequisite
and reports SKIP with the measured memory otherwise. A separate always-registered
`runtime-service-launch-host` proof verifies actual memory without inflation,
correct compiler rejection on an ineligible host (or missing-generation rejection
on an eligible host), no preview/session side effect and unavailable game launch.
The runner self-test checks 7/8/32 GiB probes and makes an unreadable probe FAIL,
not SKIP. The registry now contains 47 suites. The full 20-row session result above
is local supported-host evidence; a hosted skip does not credit that coverage.
